# Поддержка VLESS-ссылок и HTTPS-подписок в TunnelVPN

Дата: 2026-11-03. Статус: план реализации; код приложения этим документом не изменён.

## Цель

Добавить импорт подключений, которые выдаёт бот проекта `/home/enkeym/main/vpn-new`: VLESS поверх WebSocket с TLS через Cloudflare. Сохранить существующие WireGuard/AWG, несколько туннелей, маршрутизацию по приложениям и доменам, DNS, сторож и kill-switch.

Cloudflare — промежуточный сервер, а не отдельный протокол ссылок. В интерфейсе называть подключение «VLESS · WebSocket · TLS», а установленную пользователем метку Cloudflare показывать как описание. Само наличие домена или слова Cloudflare в названии не доказывает, что origin скрыт. AWG/WireGuard напрямую соединяются с сервером; обфускация AWG не скрывает IP назначения от провайдера.

## Форматы, которые нужно различать

| Ввод | Что означает | Обработка |
|---|---|---|
| `vless://UUID@vpn.example.test:443?...#Название` | Одна конфигурация подключения, share URI | Разобрать URI и сохранить профиль |
| `https://vpn.example.test/sub/UUID` | Адрес подписки; сервер возвращает список профилей или JSON в зависимости от клиента | Скачать с явным форматом, импортировать и обновлять |
| `https://vpn.example.test/sub/UUID?format=base64` | Подписка со списком URI в Base64 | Декодировать список, разобрать каждую запись |
| `https://vpn.example.test/sub/UUID?format=singbox` | JSON-конфигурация sing-box | Извлечь разрешённые VLESS outbounds, не запускать весь документ |
| `https://vpn.example.test/sub/UUID/full` | Полная конфигурация sing-box с TUN и политиками | В первом выпуске объяснить ограничение и предложить обычную подписку; не подменять настройки приложения |
| AWG/WireGuard `.conf` и QR с этим текстом | Другой протокол и формат конфигурации | Сохранить существующий импорт .conf; QR — только способ передачи содержимого |

`UUID` и домен здесь — заглушки. Реальные ссылки содержат доступ к VPN: не публиковать и не помещать в fixtures, telemetry или логи. Base64 не шифрует содержимое. HTTPS-подписка не является страницей для браузера: в браузере может отображаться служебный текст.

Пример одного профиля без действующих учётных данных:

```text
vless://00000000-0000-4000-8000-000000000000@vpn.example.test:443?encryption=none&security=tls&type=ws&host=vpn.example.test&sni=vpn.example.test&path=%2Fexample-ws&fp=chrome#Cloudflare%20%C2%B7%20TLS%20vpn.example.test
```

Для нашего сервера: UUID → `uuid`, адрес URI → `server`, порт → `server_port`, `security=tls` → TLS enabled, `sni` → TLS server_name, `type=ws` → transport WebSocket, `host` → HTTP Host, `path` → WebSocket path, `fp=chrome` → uTLS fingerprint при поддержке установленным ядром. `encryption=none` относится к VLESS; транспорт остаётся зашифрован TLS. `flow` для этого профиля не нужен; нельзя автоматически добавлять Vision/Reality или переход на origin-IP.

## Порядок реализации

1. Проверить правила проекта и фактическую версию поставляемого ядра. Минимальным конфигом и `sing-box check` подтвердить VLESS + WS + TLS + uTLS. Не обновлять форк без проверки AWG и действующих схем DNS. Если uTLS отсутствует, показать несовместимость, не игнорировать `fp` молча.
2. Обобщить модель сохранённого профиля: различать WireGuard, AWG и VLESS. WG/AWG поля оставить в существующем парсере; VLESS не превращать в поддельный `.conf`. Сохранить обратную совместимость старых данных. Вместо проверки VLESS через AllowedIPs явно задать его возможность быть основным выходом и правила назначения в существующей модели туннелей.
3. Сделать один общий разборщик входа для текста из буфера, URI, файла и результата подписки. Первый объём: одиночный VLESS WS+TLS и список таких URI, в том числе Base64/Base64URL с допустимыми переносами и отсутствующим padding. Проверять UUID, порт, host/SNI, поддерживаемые параметры; корректно обрабатывать percent-encoding, Unicode-названия и IPv6 authority. Не декодировать дважды. Несовместимые/дублирующиеся значимые параметры отклонять с понятной ошибкой. Не обещать поддержку VMess/Trojan/Reality одним общим словом «ссылки».
4. Встроить VLESS outbound в существующий сборщик sing-box и боковых процессов, сохранив приложение владельцем TUN/DNS/routes/kill-switch. Пройти путь запуска, проверки доступности, остановки, смены сети и восстановления. Проверить DNS bootstrap адреса сервера без рекурсии через ещё не поднятый VPN; избегать перехвата sing-box собственного соединения. Не отключать проверку сертификата.
5. Добавить в окно «Вставить ссылку» и «Добавить подписку», предварительный просмотр типа, имени, адреса и количества профилей. Имя из URI считать обычным текстом. Ссылки сторонних приложений `happ://`/`hiddify://` в первый объём не входят: это оболочки запуска приложений, а не новый VPN-протокол. Регистрация обработчика `vless://` в Windows — отдельный последующий шаг; для первого выпуска достаточно вставки.
6. Для нашего бота запрашивать `format=base64` явно: не полагаться на User-Agent. Сохранять параметры URL безопасно; не изменять произвольные подписки других провайдеров как будто они имеют тот же API. Общий импорт определяет формат ответа по содержимому, а не только Content-Type. Не угадывать другие пути при 401/403/404 и не терять учётные параметры при обновлении.
7. Обновлять подписки с таймаутом, ограничениями размера/числа записей и числа редиректов. Сохранить последнее исправное состояние при ошибке сети/пустом/невалидном ответе; обновлять атомарно после проверки. Указать дату и результат последнего обновления, предусмотреть ручное обновление. Использовать стабильную идентичность профиля и источник, чтобы не терять выбор и правила при переименовании; удаление выбранного профиля обработать явно. Никакого скрытого перехода на direct или прямой origin при сбое; существующую настройку выхода напрямую/kill-switch не менять молча.
8. Добавить ограниченный импорт sing-box JSON: только известные совместимые VLESS outbounds и их разрешённые поля. Селекторы/urltest можно раскрыть в список кандидатов без загрузки сторонних URL; зависимости dialer/detour и неподдерживаемые transports отклонять явно. Не принимать из документа inbounds, TUN, локальные пути, remote rule sets, clash/API listeners, DNS и route политики. `/full` нельзя исполнять как конфиг привилегированной службы.
9. Защитить сетевой импорт в контексте SYSTEM-службы: только HTTPS с проверкой сертификата; запретить userinfo и переход на HTTP; для первоначального URL и каждого redirect проверять loopback/link-local/private/metadata назначения и фактические адреса соединения, включая IPv6, IPv4-mapped и DNS rebinding. Для частных корпоративных источников предусмотреть отдельное явное разрешение, не обход по умолчанию. Не выводить полный subscription URL/UUID в логи; хранить доступ с ACL не слабее существующих ключей. При первичном импорте учитывать отсутствие работающего VPN, при обновлении — действующий kill-switch и маршрутизацию приложения, не добавлять неявный обход.
10. После focused проверок обновить пользовательскую инструкцию: различать профиль, подписку и QR. Поддержку других протоколов и автоматическое обновление по расписанию расширять после устойчивого импорта VLESS. Этот запрос разрешает подготовку плана; реализация, commit/push и выпуск не выполняются в рамках сохранения файла.

## Приёмка

- Одиночная ссылка и обе формы подписки нашего бота создают одинаковые параметры VLESS WS+TLS; имя с кириллицей и символом `·` сохраняется.
- В sing-box check проходит конфигурация именно установленного приложения; реальное подключение проверяет DNS, HTTPS и передачу данных через Cloudflare.
- WG/AWG импорт и старые профили продолжают работать; несколько туннелей, основной/списки, исключения приложений, сторож и kill-switch сохраняют поведение.
- Отказ TLS, недопустимый URI, слишком большой ответ, неверный Base64, вредоносный JSON, SSRF/redirect и обновление недоступной подписки не повреждают рабочие профили и не раскрывают секреты в ошибке.
- Нужные проверки Windows выполняются на Windows с проектным runner; тестовые данные используют только фиктивные учётные данные. Отдельно проверить IPv6, UDP/DNS и UDP-heavy приложения: работоспособность HTTPS не доказывает поддержку любого UDP-сценария через VLESS WS.
